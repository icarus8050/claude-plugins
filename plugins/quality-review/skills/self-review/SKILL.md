# 셀프 리뷰

`refactor-scan`이 "무엇을 바꿀지"를 제안한다면, `self-review`는 "이미 바꾼 것이 깨끗한지"를 점검한다.

대상 범위: `$ARGUMENTS`에 지정된 경로가 있으면 그 범위, 없으면 `git diff`(스테이징 + unstaged)로 얻은 변경분 전체.

## 점검 항목

1. **포맷터 정렬 그룹** — 자동 포맷터가 정렬을 적용하는 블록(예: Go struct literal/필드 선언, TS interface 필드, Rust struct, Python `@dataclass` 필드 등)에 line-comment를 끼워 정렬 그룹이 끊어진 곳이 없는가? 필요하면 inline 주석으로 전환한다.
2. **rename / 이동 위생** — 리네임하거나 모듈을 옮긴 식별자가
   - import된 패키지/모듈명과 겹쳐 섀도잉을 유발하지 않는가 (같은 스코프의 로컬 변수도 동시 리네임했는가)
   - 이전 이름/위치를 참조하는 orphan이 남아 있지 않은가 (`grep`로 확인)
   - **규칙·스타일 문서의 예시 코드에 옛 이름/위치가 박혀 있지 않은가** (스타일 가이드, 커밋 규칙, 테스트 규칙 등)
3. **에러 처리 일관성** — 새로 추가/수정된 에러 반환·전파점이 프로젝트의 관용구를 따르는가.
   - 언어별 예시: Go의 `fmt.Errorf("pkg: ...: %w", err)` 래핑, Rust의 `?` + `thiserror`/`anyhow`, Python의 `raise X from err`, JS/TS의 `throw new Error(..., { cause })`.
   - 비교 관용구도 통일 — Go `errors.Is`/`errors.As`, Python `isinstance`, Rust `matches!` 등.
4. **sentinel 값 + 의도적 실패 무시 정당화** — `0`, `nil`/`null`/`None`, `""` 같은 값이 "다른 곳에 기본값을 위임" 등 비자명한 의미를 가진다면 inline 주석으로 명시.

   추가로 **의도적 에러 무시**(Go `_ = err`, Python `except: pass`, JS `.catch(() => {})`, Rust `let _ = ...`)에 "이래서 무시해도 안전"이라는 약속이 붙어 있다면 그 약속이 실제 코드 흐름에서 성립하는지 검증한다. 안티패턴:
   - "다음 timeout에서 재시도"라 적혀 있지만 (a) 메모리 상태는 갱신됐는데 디스크 persist만 실패해 reboot 시 상태 불일치 — 안전 invariant 깨짐, 또는 (b) 같은 조건이 다음 시도에서 재현된다는 보장이 없음(상대 노드가 사라지는 등).
   - "fail-safe로 처리됨"이라 적혀 있지만 실제 폴백 경로가 없거나 다른 invariant를 깸.

   검증 실패 시 (1) 주석을 정확히 수정해 거짓 약속을 없애거나, (2) 처리 자체를 바꾼다(panic / fatal log / 호출자에게 에러 전파). silent drop이 진짜 의도면 이유를 "왜 무시가 정당한가"가 아니라 "이건 임시 처리, 후속에서 X로 정리"로 명시.
5. **기본값/초기화 적합성** — 언어가 zero-init/기본값을 지원하는 경우(Go zero value, Rust `Default`, Python `dataclass field default`, JS undefined 등), 그 값이 의도와 일치하면 명시적 초기화를 제거. 반대로 기본값에 의존하는데 그 사실이 비자명하면 주석으로 명시.
6. **프로젝트 규칙 재확인** — 스타일 가이드, 커밋 규칙 등 프로젝트 문서의 규칙. 주석은 "왜"에만, 데드 코드 없음, 작업 번호/호출자 주석 없음. 추가로 두 가지를 직접 확인:
   - **함수 본체 라인별 추상화 수준 일치** — 변경된 각 함수를 위→아래로 한 번 훑어 라인별 수준이 같은지 본다. 들여쓰기가 평탄해도 (literal 조립 + 흐름 분기 + count 누적) 같은 평행 혼재가 있으면 헬퍼로 추출. 들여쓰기 grep은 nesting 형태만 잡으므로 self-review가 이 평행 혼재의 1차 점검자다. refactor-scan에 떠넘기지 않는다.
   - **함수 이름이 책임과 일치** — 특히 `handle*` 접두사는 인입 dispatch에 한정 — 송신·요청을 시작하면 동사 접두사(`request*`, `send*`, `call*`)로. 한 파일에 `HandleX`/`handleY` 같이 의미가 갈리는 짝이 보이면 후자를 리네임.
7. **테스트 setup 어서션** — 회귀를 잡기 위해 추가한 테스트라면, 회귀 시점의 setup 전제(예: "고아 파일이 디렉터리 스캔에 잡히는 위치에 있다", "magic 바이트가 의도한 값")가 외부에서 관찰 가능한 어서션으로 코드에 박혀 있는가? 전제가 본문에서 인라인 주석으로만 남아 있다면 한 줄 어서션을 추가해 의도가 자기-증명되도록.
8. **빌드 / 테스트 / 포맷 / lint 통과** — 프로젝트의 검증 명령이 모두 통과하는가
   - 포맷터: 출력 없어야 함 (예: Go `gofmt -l .`, JS/TS `prettier --check`, Rust `cargo fmt --check`)
   - linter (예: `go vet ./...`, `eslint`, `ruff check`, `cargo clippy`)
   - 테스트 (예: `go test ./...`, `pytest`, `jest`, `cargo test`)
9. **문서 동기화** — 리네임/시그니처 변경이 CLAUDE.md(또는 동등 문서)의 API 기술과 일치하는가.

## 작업 방식

- 점검 항목별로 발견한 문제를 나열하고, 사소한 편집 위생 이슈는 즉시 수정한다 (설계 변경이 아니므로 승인 불필요).
- 설계/인터페이스 수준의 변경이 필요해 보이면 수정하지 말고 별도로 보고한다 (그건 `refactor-scan`의 영역).
- 마지막에 "수정한 항목 / 남은 의문" 두 줄로 요약한다.

## 금지 사항

- 범위를 벗어난 파일에는 손대지 않는다 (diff 밖 파일은 제안만).
- 벤치마크 없는 성능 최적화 변경 금지.
- 프로젝트 스타일 가이드와 상충하는 변경 금지.
