# 리팩토링 스캔

`$ARGUMENTS`에 지정된 경로(패키지/모듈 또는 파일)가 있으면 그 범위를, 없으면 `git status`로 변경된 소스 파일 전체를 대상으로 삼는다. 대상 확장자는 프로젝트 언어를 따른다(예: `*.go`, `*.py`, `*.ts`, `*.rs`).

## 스코프 설정

변경된 파일 자체만 보지 않는다. **새 소비자가 등장한 경우**(예: 새 모듈이 기존 모듈을 import하기 시작), 의존 대상 모듈의 공개 API를 소비자 관점에서 한 번 더 훑는다. 경계 재조정이 필요한 문제는 모듈 경계를 넘어야 보인다.

**의존 모듈의 비공개 헬퍼도 한 번은 훑는다.** 새 모듈이 기존 모듈을 처음 import하기 시작하는 transition은 의존 대상 코드의 가독성을 점검할 자연스러운 트리거다. 공개 API의 시그니처만 보지 말고, 그 모듈의 비공개 함수까지 한 번은 들여다본다 — 특히 들여쓰기 깊이 점검(아래)은 공개/비공개 무관하게 적용한다.

### 들여쓰기 깊이 grep

스코프 안의 모든 소스 파일에 대해 **들여쓰기 3단계 이상의 함수 본체**를 찾아 후보로 등록한다. **프로젝트의 들여쓰기 컨벤션을 먼저 확인**한다 (탭 vs N-space). 한쪽만 보면 가짜 음성이 난다.

언어별 흔한 들여쓰기 단위:
- Go (tab 1): 3단계 = 탭 3개
- Python / Ruby / JS / TS (보통 space 2 또는 4): 3단계 = space 6/12개
- Rust (space 4): 3단계 = space 12개

탭 기반:
```bash
grep -rnP '^\t{3,}[^[:space:]]' --include='*.<ext>' <scope>
```

스페이스 기반(4-space 가정):
```bash
grep -rnP '^( {12,})[^[:space:]]' --include='*.<ext>' <scope>
```

두 컨벤션이 섞이는 프로젝트라면 `grep -P '^(\t{3,}| {12,})[^[:space:]]'`로 OR. `grep -P`(PCRE)가 없으면 두 번 돌린다.

매칭된 파일은 함수 단위로 열어 `for` → 에러 분기 → 분류 분기 류의 중첩이 의미 결정을 들고 있는지 본다. 해당 시 "들여쓰기 평탄화" 후보로 보고 (루프 본체 헬퍼화 / early-return 평탄화 / 도메인 특수 케이스 호출부 이동).

**메타 함정**: grep 패턴이 들여쓰기 문자(tab vs space)나 단위(2/4-space) 한쪽만 가정하면 *모든 매치가 0개로 통과*하므로 가짜 음성을 회피한 척하기 쉽다. 새 grep 휴리스틱 추가 시 항상 알려진 양성 케이스(예: 4단계 깊이 함수)에 적용해 매치 1개+ 확인.

## 점검 항목

각 파일에 대해 아래 관점으로 검토한다.

1. **책임 분리** — 한 타입/클래스가 두 가지 이상의 독립적 관심사를 품고 있는가? (예: 기록 + 스케줄링)
2. **중복** — 동일한 기본값/로직이 두 곳 이상에 박혀 있는가?
3. **미사용 / 데드 코드 / 데드 분기** — 선언되었지만 사용되지 않는 필드·옵션·콜백 + **분기가 실행은 되지만 조건이 현재 동시성 모델에서 트리거 불가능한 dead branch**. 특히 "상태 식별자 검사"(예: `if state != X`)는 비동기 응답 모델에서만 필수 — 동기 + 락 잡힌 채 송신하는 모델에선 send 도중 자기 state 변경이 불가능하므로 검사 자체가 dead. 보통은 네트워크/raft/이벤트 라이브러리의 일반 패턴을 무비판적으로 박을 때 들어옴. "발생 불가능한 경우에 대한 방어적 검증 금지" 원칙 위반.
4. **인터페이스 / 타입 배치** — 인터페이스나 팩토리 함수가 **실제 소비자**가 있는 모듈에 있는가?
   - 인터페이스/팩토리의 호출처를 `grep`으로 확인한다.
   - 호출처가 전부 특정 외부 모듈 하나에 몰려 있다면, 해당 타입을 그 모듈로 이전할지 검토한다.
   - 특히 현재 위치가 "제공자 모듈"(실제로 그 타입을 구현/만족하는 타입이 있는 모듈)이라면 더욱 의심한다.
   - 규칙 문서의 예시("X는 Y에 있어야 함")를 증거로 쓰지 말고, **규칙의 의도**("소비자 측 정의")가 실제 구조에 반영되었는지로 판단한다.
5. **에러 처리 일관성** — 래핑 방식, 비교 관용구가 프로젝트 내에서 통일돼 있는가. 언어별 권장 관용구 예시: Go `%w` + `errors.Is/As`, Rust `?` + `thiserror`, Python `raise X from err`, JS/TS `cause` 옵션.
6. **기본값 활용** — 언어가 기본값/zero-init을 지원하는 경우, 불필요한 명시적 초기화가 있는가? (Go zero value, Rust `Default`, Python `dataclass default`, TS optional 등)
7. **추상화 수준 일치** — 한 함수가 고수준 흐름(예: 정규화 → 재생 → 오픈 → 시작)과 저수준 세부(옵션 필드 조작, 바이트 조립, 플래그 분기 등)를 한꺼번에 품고 있는가? 섞여 있으면 저수준 블록을 이름 있는 헬퍼로 추출해 호출부가 한 레벨로 읽히게 한다. **들여쓰기 3단계+** 함수가 보이면 "들여쓰기 평탄화" 세 패턴을 후보로 등록.

   **들여쓰기 grep은 한 가지 패턴만 잡는다** — 루프×에러 분류 같은 nesting 형태. 들여쓰기가 평탄해도 한 함수 본체에 (literal 조립 + 흐름 분기 + count 누적) 같은 다른 수준이 평행하게 늘어선 형태는 별도로 점검한다. 변경분의 각 함수를 한 번씩 위→아래로 훑어 "각 라인이 같은 수준에 있는가"를 직접 확인. "30행 미만이라 분리 이득 작음" 휴리스틱은 책임 분리/중복에 한정 — 단일 함수의 추상화 일치는 행수와 무관하므로 적용 금지.
8. **문서-코드 동기화** — CLAUDE.md(또는 동등 문서), 주석, 타입 문서가 실제 구현과 어긋나지 않는가?
9. **정책 비대칭** — 같은 데이터 구조에 대한 둘 이상의 호출자(또는 read/write 경로)가 같은 invariant 위반을 다르게 처리하고 있지 않은가? 의도된 분기라면 doc로 명시, 아니면 정렬한다. 예: writer는 자가 치유 / reader는 ErrCorrupt 같은 비대칭이 의도 없이 굳어졌는지 점검.
10. **버퍼링 / 성능 명백한 결함** — 명백히 불필요한 syscall, 할당 루프 등 (단, 벤치마크 없이 미세 최적화 제안 지양).

    **외부 호출 위생도 같이 본다**: 네트워크·RPC·DB 같은 외부 호출에 deadline/timeout이 없으면 무한 대기 위험. 언어별 패턴 — Go `ctx, cancel := context.WithTimeout(parent, ...)`, JS `AbortController` + `setTimeout`, Python `asyncio.wait_for` / requests `timeout=`. 호출자의 상위 컨텍스트에서 derive해 전달하는 것이 정확한 패턴. in-memory/stub 단계에선 무관하지만 실 transport(gRPC, HTTP 등) 도입 시 강제 — 자리 표시 주석 또는 즉시 교체.
11. **반환값 응집** — 함수가 `(*X, bool, error)` 같은 3+ 반환을 (튜플/구조체 분해/destructuring 형태로) 내놓으면서 두 값이 개념적으로 한 묶음이거나, 호출부가 항상 같이 쓰거나, zero 패딩이 반복되는가? 도메인 struct/record로 묶는 후보로 등록. (error는 항상 별도)

    **2-tuple도 후보로 등록하는 경우**:
    - `(bool, bool)` 같은 동질 타입 두 개 + 도메인 분류 의미 — bool 두 개의 4가지 조합 중 일부가 invariant상 불가능하면 보통 **enum이 더 자연**(3-state enum이 4→3 invariant를 타입에 박는다). struct(bool, bool) grouping은 임의 묶음에 가깝다.
    - 다중 분기에서 zero 패딩이 반복 (예: `return false, false`, `return true, false`) — 같은 의미의 zero 분기가 시그니처에 그대로 드러나는 신호.

    bool 두 개 시그니처가 보이면 1차로 enum 후보를 검토한다. struct는 두 값이 의미적으로 독립이고 동시에 의미 있을 때만.
12. **파라미터 응집** — 함수가 같은 정보 묶음을 여러 인자로 풀어 받고, 깊은 콜 체인을 따라 같이 흐르는가? 컨텍스트 struct/record로 묶는 후보. flag 파라미터(`bool`)가 함수 동작을 가르면 두 함수로 분리할지 검토.
13. **함수 정의 순서** — 프로젝트 스타일 가이드의 "함수 배치" 규칙(caller above callee, 형제 헬퍼는 호출 순서, 같은 리시버 메서드 인접, 공개 → 수명주기 → 비공개 순)을 명시적으로 점검:
    - `grep -n '^func\|^def \|^class \|^fn ' <file>` (언어에 맞춰 조정)으로 함수 순서를 펼쳐 caller가 callee보다 아래로 가지 않았는지.
    - 같은 리시버/클래스의 메서드 그룹을 자유 함수가 끊고 있지 않은지.
    - `Close`/`Stop`/`Drop`/`Dispose` 같은 수명주기 메서드가 비공개 helpers보다 아래로 밀려 있지 않은지.

## 출력 형식

- 우선순위 순(High → Low)으로 번호 매긴 목록.
- 각 항목: **제목 / 문제 / 근거가 되는 파일:라인 / 제안하는 변경 / 트레이드오프 (있다면)**.
- 마지막에 추천 작업 순서 요약.

## 금지 사항

- 사용자의 승인 없이 코드를 수정하지 않는다. 제안만 한다.
- 벤치마크 없이 "성능 개선"을 최우선 근거로 제시하지 않는다.
- 프로젝트 스타일 가이드의 규칙에서 벗어나는 제안은 하지 않는다.
